# 文档共创工作流

## 📖 说明

**独立重写版**。原版 `doc-coauthoring` 没有附带许可文件，为稳妥起见按
「不可再分发」处理，这里不克隆、只重写其**三阶段工作流**的核心思想。

## 核心理念

**文档写不好的根本原因，通常不是文笔，是上下文没交出去。**
写的人脑子里有一堆隐含前提，读者没有，于是文档「自己看得懂、别人看不懂」。

所以这个工作流只做三件事：

```
① 收集上下文  →  ② 逐节打磨  →  ③ 读者测试
   （把隐含前提显式化）  （结构先于文字）  （用没有上下文的读者验证）
```

## 什么时候该走这个流程

- 用户说「帮我写个方案 / 规格 / RFC / 决策文档 / 评审材料」
- 用户要开始一项**篇幅较大**的写作任务
- 用户已经有一份草稿，想改进

**先问一句**：要不要走这个结构化流程？还是直接自由发挥？
用户说不用，就自由发挥——不要强推。

## 阶段一：收集上下文

**目标**：把用户脑子里的东西搬到台面上。

### 先问 5 个元问题

1. 这是什么类型的文档？（技术规格 / 决策文档 / 方案书 / 报告）
2. 主要读者是谁？（评审专家 / 领导 / 合作方 / 未来的自己）
3. 读完希望他们产生什么行动或判断？
4. 有没有必须遵循的模板或格式？
5. 还有什么约束是我该知道的？

**如果用户有模板**：要过来，先读，按它的骨架走。

### 然后让他「倒」上下文

明确告诉用户：**不用组织，想到什么说什么**。要的东西包括：

- 项目/问题的背景
- 相关的讨论、已有材料、链接
- **为什么其他方案不可行**（这条最有价值，也最容易被漏掉）
- 组织层面的情况（团队、历史包袱、过往事故）
- 时间压力与硬约束
- 技术架构与依赖
- 各方关心的点

## 阶段二：逐节打磨

**不要一次写完**。一节一节来：

1. 先和用户对齐这一节的**大纲**（3-5 个要点）
2. 确认后再展开成文字
3. 用户看完给反馈，改
4. 再进下一节

**结构先于文字**。如果一节的结构不对，写得再漂亮也是白搭。

**每节写完自问**：
- 这一节回答了读者的哪个问题？
- 有没有隐含前提没写出来？
- 有没有术语没定义？

## 阶段三：读者测试

**这是最容易被跳过、但最有价值的一步。**

做法：**换一个没有任何上下文的读者**（换一个会话/子代理），
把文档丢给他，问他：

- 你看完理解了什么？
- 哪里看不懂？
- 如果要你执行，你会怎么做？有歧义吗？

**为什么要这么做**：写的人会不自觉地「脑补」，只有陌生读者才能暴露盲点。

**特别注意**：文档里的**图片**，如果读者是 AI，是看不到的。
检查有没有图缺 alt 文本，缺了就补。

## 交付前自检

- [ ] 每节都有明确的小标题
- [ ] 术语首次出现处有定义
- [ ] 没有未解释的缩写
- [ ] 结论和依据分得开（**别把推测写成事实**）
- [ ] 需要读者决策的地方，选项和取舍都列了
- [ ] 有下一步 / 行动项

## 诚实性要求（技术文档尤其适用）

- **区分事实、数据、推测**——推测必须标注为推测。
- 数据要能追溯来源。选型表的实测值、论文值、理论假设，
  三类来源**分开标注**，不混着写。
- 不确定的地方就写「不确定」，不要用模糊措辞糊过去。
